# AI in a Megalo (multiplayer) game

Issue #247 (bots to fill lobbies), route B: can the simulation's own AI play in
a Slayer match? Spike run 2026-10-25 on CU4, one PC, host only.

## The test map

`examples/levels/bot_b40_beach.level.json`, baked as the standalone codename
`BOT`:

```bash
mjolnir level bake examples/levels/bot_b40_beach.level.json --standalone BOT --install-test
```

It is B40 (The Silent Cartographer) under the Megalo engine on B40's **stock**
BSP 8 (`bsp_01_1_start`, the Forerunner interior at insertion point 0), with
the mission's squads, squad groups, zones, AI objectives, character palette and
`ai pathfinding data` kept (`clear.squads: false`, none of those in
`clear.blocks`). No `single_bsp`: squad spawn points name their BSP by index
(`structure bsp #8`) and the single-BSP pass does not remap them. Four player
starts and `player_spawn` scenery sit on B40's own insertion-0 starts.
Only four squads stand on BSP 8: `insertion_cov_grunts_flee`,
`insertion_cov_grunts_interior`, `insertion_cov_elites`,
`pelican_arrival_squad`.

Hosted with `mjolnir_auto host BOT slayer private`. AI is placed with
`mjolnir_sim_script` lines (MJOLNIRLobby's DLL, sim thread), never with the
Blam console from Lua mid-game.

The script path reports nothing back, so results were read with colour fades:
`(if (> (ai_living_count insertion_cov_elites) 0) (fade_out 0 1 0 5) (fade_out 0 0 1 5))`
turns the screen green or blue.

## Findings

1. **`ai_place` is a no-op in a multiplayer game.** Its core
   (`sim+0xfd810`, called from the `ai_place` evaluator `sim+0x1c0240`) runs
   only when the game options' mode byte (`[TLS+0x60]+0x10`, the same options
   block whose `+0x15f0` holds the live variant) is 1 (campaign) or 2
   (Firefight, with options `+0` or `+1` set). A Megalo match is mode 3, so
   the squad is never placed. `ai_enabled` is true throughout.

   ```text
   sim+0xfd839  80 78 10 01   cmp byte [rax+10h], 1
   sim+0xfd83d  74 22         jz  +0x22   ; campaign: place
   ...                                    ; else mode 2 check, else return
   ```

   Patching `sim+0xfd83d` `74 22` → `eb 22` (always place) makes `ai_place`
   work in the Megalo game. No other gate was needed for what follows.

2. **Placed AI think, path and fight under Megalo.** Elites and Grunts spawned
   at their squad spawn points, walked tens of metres through the BSP towards
   the player (pathfinding from the kept `ai pathfinding data`), shot, and
   killed the player. The Pelican of `pelican_arrival_squad` flew in. Placing
   the same squad again adds its members again.

3. **Incidents carry AI kills both ways**, through the same
   `BPC_MeteoriteIncidentHandlerComponent:OnIncident_Event` the HUD hooks:

   | Event | Cause | Effect |
   |---|---|---|
   | AI kills the player: `death` (no `Kill`) | index −1, `CauseObjectActor` = `BP_GruntBipedActor_C`, damage `PlasmaPistol` | index 0, `BP_SpartansBipedActor_C` |
   | player kills AI: `Kill`, `auto_kill`, `kill_elite` / `kill_grunt`, `kill_enemy_leader`, `headshot_kill` ... | index 0, the player's biped, damage `AssaultRifle` | index −1, `BP_EliteBipedActor_C` / `BP_GruntBipedActor_C` |

   Megalo respawned the dead player after the variant's 5 s, with the usual
   `respawn_tick` / `player_spawn` incidents.

So a bot's kills and deaths can be told apart from players' by player index
−1 and recognised by their biped actor. A scoreboard row for a bot is
bookkeeping in the HUD's match model, keyed by the AI biped, with no sim work.

## Since the spike

Bots now play on Blood Gulch, host and joiner ([../bots.md](../bots.md)).
Answered since:

- **Fireteam clients** see the host's AI move and fight (two PCs,
  2026-10-25): the simulation replicates them; positions of AI far from the
  joiner's player lag a few metres.
- **Converted maps' pathfinding** is generated by the bake
  (`blam_sbsp::pathfinding`). The format, read off B40: `sectors` (8 bytes:
  flags, hint, first link), `links` (16: vertex 1, vertex 2, flags, hint,
  forward, reverse, left sector, right sector; forward continues the left
  sector's ring, reverse the right's), `bsp2d refs` one per collision surface
  of the BSP or object (a sector index, `0x80000000 | node` into `bsp2d
  nodes`, or -1), `vertices`. B40's own sectors all lie on instanced geometry
  (its `object refs`, one per definition), and its BSPs set `no default
  structure pathfinding`; a converted map's shell carries the sectors, so the
  bake clears that flag.
- **A scenario with AI needs `ai user hint data[0]`.** `sim+0x16d020` reads the
  block's first element without checking the count (AV at 0x48 on Blood
  Gulch, whose bake had cleared the block). The bots lane keeps one element,
  every hint list emptied.

## Steps and seams in Bungie's pathfinding

Read off the shipped scenarios with `pf_dump <scenario> <sbsp> <bsp> raw`
(and `risers`, `shell` for a converted shell) on 2026-10-30, to let bots
cross the lips and cracks of converted maps (`blam_sbsp::pathfinding`).

**Flag names** come from the tag definitions (`defs/hce/tag-definitions.json`).
Sector flags: walkable 0x1, breakable 0x2, mobile 0x4, bsp source 0x8, floor
0x10, ceiling 0x20, wall north 0x40, south 0x80, east 0x100, west 0x200,
crouchable 0x400, aligned 0x800, step 0x1000, interior, rail, user. Link
flags: from collision edge 0x1, intersection link 0x2, bsp2d creation error
0x4, topology error 0x8, chain error 0x10, threshold 0x20, wall base 0x40,
ledge 0x80, leanable 0x100 (low 0x200, high 0x400), start corner 0x800, end
corner 0x1000, seam 0x2000.

**Steps.** Across B40, A30, A50, B30, C10 and D20 (about 150,000 sectors)
the only sectors that are not `walkable | floor` (0x11, or 0x15 on objects)
are steps: `walkable | step | wall <one direction>`, no floor bit. A short
riser is a sector of its own, linked to the floor above and below through
its edges (flags none or threshold). Most are on one object B40 repeats in
every BSP (rises 0.007 to 0.078 wu, sloped up to nz 0.49); four lie on
structure, pure vertical risers of 0.03 and 0.04 wu with normal (-1, 0, 0)
flagged `walkable | wall west | aligned | step` (0x1a01). So -x is west; the
generator takes +y as north. The shipped `ai_globals` say where a step ends:
`hoist step` is (0.1, 0.4) wu and `max jump down height down` 0.1, so a rise
under 0.1 wu is walked, anything taller hoisted or jumped.

**Intersection links** join sectors on separate geometry (every B40 instance
boundary; 194 hints in BSP 8 alone, all of type 0 `intersection link`):

- each sector keeps its own boundary link along the seam (`right sector`
  -1), flagged `intersection link` (0x2, most often alone) with a hint of its
  own: no hint serves two links;
- the hint is `(type 0, next, data (joining link, 0, 0, 0))`; about one in
  five carries `data1 = 1` and two more numbers (a piece and an index, it
  seems) that the zero form does without;
- both hints name one two-sided link, all of them after the regular links:
  its vertices are the first link's (`left sector` the first's sector), its
  `forward link` is the first link's, its `reverse link` the second link's
  `forward link`, flags 0 or threshold, no hint. It is in neither ring;
- a sector's `hint index` heads a chain (`next hint index`) of exactly the
  hints of its own ring's links (632 of 632 sectors in BSP 8), -1 without.

The B40 pieces' seams coincide exactly. Converted maps built of slabs leave
cracks: Night Lockout's floors end in their slab's own side face, with the
next slab's floor edge to edge, 0.01 wu inside or up to about 0.1 wu away.
The generator joins two floor edges that both drop away, run opposite ways
within 0.1 wu and lie less than a step apart in height, cutting each link at
the shared stretch's ends first so the joining link spans exactly it.

**Player starts** in the hub maps' level files stand 1.0 wu above their
floor (every start of Night Lockout, Blood Gulch and Boarding Action; with
the spawn lookup allowing 0.25 wu, no hub map loses a start).

## Teams in a Megalo match

Read with Ghidra (`C:\ghidra_proj\sim\HaloSim.gpr`, headless GhidraMCP on
port 8089) and measured live on Blood Gulch in Team Slayer, 2026-10-30,
with `mjolnir live objects`, which now prints each unit's team pair.

**A unit has a team pair** at datum `+0x1ba`: a campaign team (the squad
enum: default 0, player 1, human 2, covenant 3, brute 4, mule 5, spare 6,
covenant_player 7, flood 8, sentinel 9, heretic 10, prophet 11, guilty 12,
berserk_hostile_to_all 13) and a multiplayer team (red 0, blue 1, ...; -1
for none). `unit_get_team_index` (sim+0x1bacc0) returns the first byte.
Measured: a player's unit is **-1/0** (no campaign team, red); every bot is
**3/-1** (covenant, no multiplayer team).

**The unit update sets the pair every tick** (sim+0x5f6c60): from the
controlling player's pair (players array `+0xac`) for a player's unit; for
an AI's unit, `actor+0x2c | 0xff00` at sim+0x5f87bf..0x5f87c9:

```text
5f87bf  0f b6 54 08 2c        movzx edx, byte [rax+rcx+0x2c]   ; actor campaign team
5f87c4  66 81 ca 00 ff        or    dx, 0xff00                  ; multiplayer team -1
5f87c9  66 41 89 97 ba 01 00 00  mov [r15+0x1ba], dx
```

A multiplayer team written into a bot's unit from outside is back to -1
within 50 ms.

**Who is an enemy.** The team tests (sim+0x26b670 friend, +0x26b710
enemy, +0x26b7a0, +0x26b920 by campaign team) branch on the game options'
mode byte (`[TLS+0x60]+0x10`). In campaign and Firefight they compare
campaign teams through the allegiance matrices at `[TLS+0x130]+0x144` and
`+0x184` (16 rows of 16 bits; `ai_allegiance` edits them). In a Megalo game
(mode 3) they ask the game engine (vtable `+0x1b8`, sim+0x20bab0) about the
two **multiplayer** teams when both sides have one, and otherwise fall back:
+0x26b710 says enemy, +0x26b670 friend.

Measured in Team Slayer:

- **Bots and players.** With no multiplayer team, a covenant bot attacks
  every player, red or blue alike, and flood, sentinel, heretic, berserk,
  brute, mule and spare bots ignore players. With the store above patched to
  give AI units a multiplayer team, bots made blue (`brute`) killed the red
  player. A single first sighting of a covenant bot on red walking up to the
  red player without firing did not reproduce: see the isolated runs under
  "Red and blue bots" below. An AI unit with a multiplayer team, whichever,
  attacked every player, because an AI picks enemies by campaign teams and a
  player's is -1 (see "How an AI picks its enemies").
- **Bot and bot.** Decided by campaign teams, multiplayer teams or not: two
  covenant bots never fight; covenant and flood fought at once (one dead in
  under a minute); covenant, flood, sentinel and heretic bots all fought one
  another. `berserk_hostile_to_all` set with `ai_set_team` did not make two
  bots of that team fight.

**Script functions.** `ai_set_team` (sim+0x1c55a0) works in a Megalo game:
it writes each actor's team (`+0xe7`, the actor datum `+0x2c`) and the unit's
pair (team, -1), and later `ai_place`s of the squad take the team too.
`ai_allegiance` (sim+0x1c3790) has the same campaign/Firefight gate as
`ai_place` and does nothing in a Megalo game. `mp_ai_allegiance` and
`mp_allegiance` share a no-op evaluator (sim+0x1b1c10: it evaluates its
arguments and returns); `player_override_team` is a stub. Nothing a script
can call gives an AI unit a multiplayer team.

**The board, before sides.** MJOLNIRHud sorts a bot into red or blue by its
biped's colour when an incident names it, so a bot with no team could land on
the player's side and its kills of that player counted as betrayals (-1).

### Red and blue bots (MJOLNIRLobby's DLL)

`mjolnir_bots_teams` replaces the store's `or dx, 0xff00` (5 bytes) with
`call` to a stub allocated within rel32 reach of the simulation DLL:

```text
push rcx; push rax
lea  rcx, [rip+0x17]        ; a 256-byte table, 32 bytes in
movzx eax, dl               ; the actor's campaign team
mov  dh, [rcx+rax]          ; its multiplayer team, 0xff for none
pop rax; pop rcx; ret
```

Flags and `edx` are dead after the store (it jumps to a call whose callee
loads `edx` first), so the stub need not keep the `or`'s flags. The table
comes from `native\bot_teams.txt` (`<campaign> <multiplayer>` per line;
the HUD writes `3 0` and `8 1`); a team the file does not name stays 0xff,
so only the bots' own teams change. The call goes in and out on the
simulation thread at the main tick, while the table is not empty and the
game options' mode byte is 3; the file emptied, or any other mode, puts the
five bytes back. A one-hit byte search finds the store, as for `ai_place`.

Measured on Blood Gulch, Team Slayer, PC 1: `3 -1` installs the call with no
change (bots stay 3/-1), `3 0` makes them 3/0 on the next tick, and an empty
file puts `66 81 ca 00 ff` back. With the HUD choosing sides (covenant red,
flood blue), a host on red and eight bots split red 3, blue 5; the units read
3/0 and 8/1; red and blue bots fought at once, and the bipeds' own team
(`BlamGameTeam`, read by the board) said `EBlamMultiplayerTeam::Red` and
`Blue` to match.

**Friendly fire, isolated** (2026-10-31): no HUD bots, the table set by hand,
one grunt placed by script on red (multiplayer team 0) at the far base, the
red host walked up to it with no other AI on the map and no shot fired. As
covenant (`3 0`), as sentinel (`9 0`) and as human (`2 0`), the grunt opened
fire within a second or two of the host coming near and killed him. The hit
records on the host's actor name that grunt with `bDamagedByFriendly` set,
and no incident came before the first hit. So the damage code calls these
hits friendly while the AI chooses the player as a target anyway: the
actor's choice of target does not run through the team test above (see the
next section). Fixed by giving players their side's campaign team; the same
isolated runs then held fire (below).

### How an AI picks its enemies

Read in Ghidra, 2026-10-31.

- **The perception record.** When an actor notices an object (sim
  0x7ade0) it makes a record of 0xb0 bytes (`[TLS+0x70]`): `+0xac` the
  object, `+0x2c` its team, `+0x2e` enemy, `+0x2f` friend. For a unit the team
  is the unit's **campaign** byte (`+0x1ba`), and the flags come from campaign
  teams alone: enemy when either side's team is -1, none when both are the
  same, otherwise the allied matrix (`[TLS+0x130]+0x184`) decides; friend is
  the friend matrix (`+0x144`). No game mode check, no multiplayer team.
  `ai_set_team` (sim+0x1c55a0) recomputes every record the same way after it
  sets the squad's actors (sim+0x59870: actor `+0x2c`, unit pair `(team, -1)`).
  Other AI code (sim+0x177710, +0x10e560, +0x12f270, +0x117790, +0x105060
  and more) calls the campaign test sim+0x26b920, which is the same rule.
- **A player's unit.** The unit update (sim+0x5f6c60) copies a player's
  unit pair from the player (`[TLS+0x30]` table, datum 0x4b0: `+0xac`
  campaign, `+0xad` multiplayer) every tick. In a Megalo game the campaign
  byte is -1, so every AI marked every player an enemy, whatever the
  multiplayer teams: the 2026-10-30/31 runs where bots of any campaign team
  with a multiplayer team shot the host.
- **The Megalo rule.** The team tests (sim+0x26b670 friend, +0x26b710
  enemy) ask the game engine (vtable `+0x1b8` through sim+0x20bab0) when both
  multiplayer teams are set. The engines sit in a table at sim+0xbd5210 by
  type (1 sandbox, 2 megalo, 3 campaign, 4 survival); Megalo's `+0x1b8` is
  sim+0x3ff050: in a team game it maps each team to a designator
  (sim+0x408c50), equal designators are not enemies and designator 8 is
  nobody's enemy; without teams it compares the players on those teams. The
  damage code goes this way, which is why a red bot's hit on the red host was
  flagged friendly.

**The fix.** While the bot team table is in, the lobby DLL writes each
player's `+0xac` from their multiplayer team (red covenant, blue flood: the
table read backwards) on the simulation thread each tick, and puts back only
a byte it wrote (by the player's salt and the value). Isolated, Blood Gulch,
PC 1: a red covenant grunt beside the red host (now 3/0) held fire 35 s;
with the table turned around (`8 0`, `3 1`) a grunt moved to flood before
its `ai_place` held fire beside the host (now 8/0), so a squad set before
placing also perceives as its new team; a covenant elite (3/1) placed beside
them took the host's shields in seconds (`bDamagedByFriendly=false`).

`ai_set_team` before a squad's first `ai_place` works too: a squad never
placed, set to flood and then placed, came out 8/1 with no second call. The
HUD sets each squad's team before placing it, because placed covenant and
moved after, a blue bot spent a tick on red, long enough for
MJOLNIRLevelLoader to tint a blue Spartan's armour red as it appeared.

**`player_get n`** (evaluator sim+0x1b21e0) asks sim+0x187880 for the nth
valid datum of the players table, counting from 0 in table order, and
returns that player's unit (`+0x28`). So `n` is a rank among the players
there are, not an absolute index: the same thing only while no seat below
is empty.

**A kill no incident reports.** When an AI kills an AI the game raises no
`Kill` and no `death` (both are about players), only kill medals such as
`first_blood`, with cause and effect -1. The UE side does know:
`BlamObjectDamageComponent` has `IsDead()` and an `OnDamageAftermath`
delegate, and the bipeds' base blueprint (`BP_BaseBipedActor_C`,
`OnBipedDamageAftermath`) keeps the latest `BlamDamageAftermathResult` in
the actor's `Blam Aftermath Result`: `DamageOwner.DamageOwnerObject` (the
attacker's biped actor), `DamagedObject`, `DamageReportingInfo` (the same
`Type`/`Modifier` the incidents carry), and `Flags` (`bBodyDepleted` on the
killing blow, `bDamagedByFriendly`, `bKilledInstantly`, ...). A body stays
an actor where it fell, and its components stay active until the simulation
deletes the corpse (`BlamObjectSynchronization.BlamObjectGameStateIdentifier`
is the object's index, the same as `live objects` prints). A unit killed by
`unit_kill` takes no damage, so its aftermath is an older hit's.

## Bots frozen in place

Measured on Blood Gulch, Team Slayer, PC 1, 2026-10-31, with eight HUD bots
and the host idle, positions read every second with `mjolnir live objects`.
Three different things kept bots still for minutes.

### A sleeping body

A blue Spartan (squad `spartan_legendary_5`) stood at (27.82, -97.41, 1.43)
for five and a half minutes: position to 0.01 wu and facing (158.4°) the same
in every sample, at full health, then shot down to 65% without moving or
turning. It stood on plain ground of the map's one walkable area. Yet:

- **Its AI was running.** Its actor (the actor array `[TLS+0x28]`, 0xd10
  bytes; a unit names its actor at `+0x1ac`, an actor its squad index at
  `+0x3c`) changed 22 of its 4-byte fields in 3 s.
- **Orders reached it.** `ai_set_task` changed its squad's task (the squad
  array `[TLS+0x58]`, 0xec bytes: task index at `+0x96` and `+0x9a`, 0 for
  `hunt` and k + 1 for `area_k`; the tick it was set at `+0x9c`).
- **Nothing an AI script call does moved it**: `ai_set_task` to areas near
  and far, `ai_force_active` (sim+0x1c5070), `ai_braindead false`.
  `ai_allow_dormant` is compiled out (it shares the no-op evaluator
  sim+0x1b1c10), as are the globals `havok_disable_deactivation` and
  `havok_deactivation_reference_distance`.
- **`(object_wake_physics (ai_get_unit spartan_legendary_5))` did**: it
  walked off within a second and fought on.

**What the wake does.** `object_wake_physics`'s evaluator (sim+0x1b5950)
calls sim+0x5a5eb0 on the object. For an object with Havok physics (object
data `+0xdc` bit 0x100, physics index `+0xcc`), it activates each of its
rigid bodies (sim+0x70b520 clears the body's deactivation counters at
`+0x162` and `+0x164` and wakes its simulation island), clears `+0xdc` bit
0x400 and marks the object and its parents active (sim+0x59f470: bit 2 of the
object table entry's flags).

**Every still body sleeps.** A watcher that read four bots still for 30 s
found the same state in each: `+0xdc` 0x8500 (bit 0x400 set), the rigid
body's `+0x164` 0xc000, its island's activity fields (`+0x10` to `+0x1f`)
zero, where moving bots had 0x8100, other values at `+0x164` (a live
counter) and live fields. The idle host's
body sleeps too. So a sleeping body is the normal state of anything standing
still; what went wrong with the Spartan is that its AI, wanting to move,
never woke it. Why not is not known.

### The flag rooms

Blood Gulch's bases have a lower floor (z -0.29) under the deck (z 1.70),
where the flag stands, open to the deck through a hole in its middle and to
the outside through a ramp at each end. The bots that stood longest were
there, on both bases, and waking them did not help: a jackal stayed over
half an hour, a grunt over 20 minutes; ordered elsewhere every 2 s, each
walked about the room, to the foot of an exit ramp and back, and stopped.
The trapped grunt and jackal held paths (four points from actor `+0x8c8`)
that began at the foot of an exit ramp and did not change with their orders.

**The bots stand on a copy of the map's collision.** A converted map's
collision is there twice: as the BSP's collision shell, and as instanced
geometry instance 0, whose definition is a copy of the shell (the same
surfaces and edges in the same order, its vertices offset by the instance's
position; `pf_where <sbsp> copies`). The BSP's Havok body, what bipeds stand
on, lists the copy's surfaces ([../ce_map_conversion.md](../ce_map_conversion.md)
"The structure BSP"). A biped's ground record in its unit datum says which
one it stands on: `+0x9e4` the collision surface, `+0x9e8` the sector
(`sector << 16 | structure bsp`), `+0x9ec` the instance, -1 for the shell.
Every bot's records, read twice a second (PC 1, 2026-10-31; one match of
150 s and three of 9 to 10 minutes, in one of which four bots were
teleported into the rooms with cutscene flags):

| Where | On the copy |
|---|---|
| The flag-room floors | 87 to 100% (1,105 records, from the three matches with bots there) |
| Their exit ramps | 15 to 100% |
| Everywhere else | 39 to 69% |

**On the copy an AI is on no sector.** `FUN_180140ac0` (sim) turns a
contact into the AI's location through `FUN_180139e00` and `FUN_18013a080`.
For the shell it reads the shell's `bsp2d refs`; for an instance it reads
the instance's `instanced geometry refs` entry (`pathfinding object_index`)
and that object's refs. The bake gives every instance -1, and no record on
the copy carried a sector (0 of about 21,000 in five matches). The actor
then keeps the last place it stood on the shell (actor `+0x4f0`, the sector;
`+0x4f4`, the point). A bot with a path walks it on the copy (bots crossed 50
to 90 wu without a record on the shell); one that needs a new path plans
from that last place, and when `FUN_180099e30` cannot resolve its movement
goal from there the path is dropped (actor `+0x87c` 0), the follower's state
(`+0x874`) is 3 and its count of failures (`+0x878`) climbs. The bot does
whatever else its AI does, and wanders, until a record on the shell gives it
a location again. In four matches the follower was in state 3 in 29 to 48%
of all samples. On the flag-room floors the shell hardly ever came, so a bot
left only if its wandering took it onto an exit ramp; beside the bases it
came late too.

Seen in a match (eight HUD bots, four teleported into the rooms with
cutscene flags, paths read four times a second):

- an elite in the south room kept, for two minutes, the goal and one-point
  path it had before the teleport (state 3), while the HUD's orders changed
  its squad's task three times; it wandered the room, stepped onto the foot
  of the north exit ramp and planned at once (a four-point path out, state
  1) and walked out;
- a jackal in the north room's middle, between the wall slabs, stayed 3
  minutes, until it wandered into the north wing and up the ramp;
- bots that had walked in planned paths on the ramps and fell back to state
  3 each time they stepped onto the floor.

The stored paths fit: each began where its bot last stood on the shell, the
foot of an exit ramp. In a match with no teleports a bot wandered the south
room for over five minutes (still there when the log stopped), and the HUD
(below) placed 19 bots again in 10 minutes, 10 of which the simulation shows
never left a 6.5 wu circle in those 55 s, beside or inside a base, in state
3 most of the time.

**Rounding picks the copy; the bake lowers it.** The copy's planes, moved to
the instance's position, sit 4.2e-6 wu off the shell's at the median and
4.4e-5 at most (`pf_where <sbsp> copyz`): the copy is placed 113 wu from its
definition's origin, where an f32 holds about 8e-6. Which of two such
surfaces a query meets is down to that rounding. Of the 222 surfaces bots
stood on often (8 records or more in four matches) whose copy's plane is in
front of the shell's, 195 gave the copy in 95% of their records or more; the
2 that gave the shell so both have the copy's plane behind. Since 2026-10-31 the bake lowers every
copy of the shell 0.001 wu (`blam_sbsp::pathfinding::lower_shell_copies`),
twenty times the largest offset and a third of a millimetre. Three
10-minute matches on Blood Gulch, eight bots and the host idle, the first on
the earlier bake and two with the lowered copy (the game held the lowered
position; the other five instances kept theirs):

The copy still takes half the records or more (50 and 57% in the open; on
the flag-room floors from 49% to all of them, over few records), and 226 of
the 423 surfaces read 8 times or more still gave the copy in 95% of their
records (329 of 458 before), yet the AI keeps its place: what it plans from
does not follow that record alone.

**Not the cause.** The weapons around the flag: an AI steers around the
pathfinding spheres of objects within 6 wu (`FUN_180177710`, object types
`0x14cb`, no weapons), no ordinary object in this game has a collision
model (the shipped ones are a hologram, an explosion and Seraph debris), and
the obstacle planner `FUN_18016d150` is off (`0x182c2ea48` 0). The teleporter
sender over one exit is a data pad without a collision model, and the
Banshee over the other is not spawned in Slayer. The graph: every sector's
ring holds all its links (`pf_where <sbsp> rings`). The walls do lean over
the floor (0.1 to 0.2 wu at 0.8 wu up, more under the side ramps beside the
flag; `pf_where <sbsp> overhang`), but bots are 0.15 to 0.18 wu in radius,
and lowering the copy ended the stays without touching the walls.

**The copy cannot be given pathfinding.** An object for it (`object refs[0]`
with one BSP entry whose refs are the shell's, and `instanced geometry
refs[0]` 0) lets the copy's surfaces find the shell's sectors, and the game
crashed (an access violation in ntdll, with no Unreal crash report) 2 to 5 s
after the bots began to move, twice. With every ref -1 it crashed after 27
s. Bungie's objects carry sectors and vertices of their own (`vertex
offset`), which these do not.

**What the HUD does.** For bots that stay put for any reason (lost on a
map's copy, a body that stays asleep, an elite under a lintel, a bot idle
under its orders), the HUD gets a bot out: one that stays within 6 wu for 40
s is woken and sent to an area that does not hold it, and if 15 s later it
has neither left nor reached that area, it is erased and placed again on a
start, as a respawn without a death ([../bots.md](../bots.md) "Stuck bots are
placed again"). The areas come from the map's `bots.json`, which the same
bake writes. Wandering wider than 6 wu defeats it: the bot in the south room
above moved about the room and was never sent.

It goes by the bot's actor, and a placement sometimes takes an actor that
stays where the bot came in while the bot walks off: six of the first eight
bots in one match, their actors exactly on their starts (the five read each
carried its bot's unit index as `BlamObjectGameStateIdentifier`), and three
more in the third match above. Placing such a bot again only takes another such
actor (in a run without the next rule, one bot was placed again five times
in five minutes), so the HUD judges only a bot whose actor it has seen move
since placing it. That leaves the HUD blind to those bots: it reads deaths
from the actor too.

In the table's matches the simulation shows, of the bots placed again, 10 of
19 that never left a 6.5 wu circle in those 55 s on the earlier bake, in
state 3 most of the time, and 6 of 12 and 5 of 12 on the lowered copy, idle
(state 0; one bot through four lives) or following a path without moving.
The rest were bots whose actors stood 5 to 27 wu from any bot, or that moved
more than 6.5 wu by the simulation's reading, which the HUD reads at other
moments. The third match ran without the rule above.

### Elites in the side doorways

The ramp from each base's deck down to a side door (sectors 1823 and 1902 on
the north base, 1824 and 1903 on the south) climbs 1.57 wu over 2.6 wu and
passes under the door's lintel, a slab whose underside is at z 1.50 (the
south-west one is surface 4333, x 90.59 to 91.31). At the lintel's inner edge
the ramp is at z 0.68, leaving 0.82 wu; an elite stands 0.8 wu (`elite_ai`
biped, `physics.height standing`; crouching 0.69, radius 0.18), against 0.65
for the Spartan, 0.7 for the jackal and 0.55 for the grunt. Seen twice on its
own and three more times on purpose (below) at the same spot: on the south
base's west ramp at (91.5, -159.5, 0.83) for five minutes, and on the north
base's east ramp at (44.18, -79.26, 0.83), facing the door, its position
twitching by a few hundredths across the ramp and its facing by a few
degrees, x fixed, until it turned back up and jumped off the deck's rim.

**Why there.** The body is an upright capsule, and on the ramp its origin
stands 0.036 above the surface (measured; a radius-0.18 sphere resting on a
31° slope sits 0.03 higher than on flat ground). Walking down, its top
reaches the lintel's lower inner corner before its axis is under it: a
capsule of height h and radius r reaches (h − r)·n_z + r + lift·n_z out from
the ramp's plane (n_z = 0.856), and the corner is 0.82·n_z = 0.70 out. For
the elite that is 0.742, so it touches with its centre 0.17 to 0.19 uphill of
the edge, where it stands. The rule gives h ≤ 0.754 for this ramp, but
measured with the capsule itself (below) 0.72 jams and 0.71 passes, so the
real limit is about 0.04 under the rule (why is not traced). A crouched
elite (0.69), the jackal (0.7, radius 0.18), the
Spartan (0.65, 0.175) and the grunt (0.55, 0.15) are under that limit.

**`crouchable` does nothing.** Bungie's sector flags include `crouchable`
(0x400). The bake never sets it, nor do the shipped scenarios read above (B40,
A30, A50, B30, C10, D20).
Tested live on PC 1, 2026-10-31, Blood Gulch Slayer with the HUD's bots
cleared: `elite_legendary_13`, blind and deaf, placed on the south deck and
ordered to `area_0` (the route runs down ramp 1824):

- it jammed at (91.50, -159.5, 0.83), three runs out of three;
- the `sectors` block, found by a run of its bytes (`pf_where hex`), exists
  once in all the game's readable memory, so that copy is the one the AI
  reads. Setting 0x400 on 1824 while the elite stood jammed changed nothing
  in 30 s, nor did ordering it to another area and back;
- with 0x400 on all four ramps, the elite erased, placed again and ordered,
  it jammed at the same spot.

The simulation's code agrees. An actor's stance is decided once a tick
(sim+0x9bb40) and handed to sim+0x611d0, which sets the unit's crouch (actor
`+0x7f8` bit 4, `+0xca0` bit 0): the value is the actor's crouch request at
`+0x790` or `+0x791` (or `+0x6b8 == 1` in another mode). About twenty
functions write `+0x790`, each from its own state: sim+0xb55a0 compares a
value at `+0x5f4` (the actor's danger, it seems) with two thresholds of its
character, sim+0xc5960, sim+0xbc160 and sim+0x176280 copy it from their own
records, and `cs_crouch`'s evaluator (sim+0x1dd310) writes the command
script's `+0x169`, which sim+0x90690 copies to `+0x790` and `+0x791`. None of
them reads the path or the sector under the actor. The only other caller of
sim+0x611d0 (sim+0x5e5bc0) clears crouch.

**Leaving the ramps out strands the decks.** Without sectors 1823, 1824, 1902
and 1903 each deck is an island of 85 sectors (`pf_where <sbsp> cut
1823,1824,1902,1903 <points>`): the ramps are the only walking way onto a
deck, and four of the fifteen bot starts stand there. An elite on a deck
still leaves by dropping over its rim (seen), but no bot could walk in to a
player there.

**The capsule is built at load.** What collides is not `physics.height
standing` but `physics.pill shapes`, empty in the shipped tag and filled at
load from the two heights and the radius. Its two elements are Havok
capsules in place (`hkpCapsuleShape`: vtable, type 5, radius at `+0x40`,
vertices at `+0x50` and `+0x60`): standing from z 0.18 to 0.62 with radius
0.18 (0.8 tall), crouching to 0.51 (0.69). Every `elite_ai` uses them, so a
write to the standing element's upper vertex (z at `+0x58`) changes elites
already placed. Writing `height standing` (`mjolnir poke ... --field
"physics.height standing"`) changes the root scalar only: elites placed after
setting it to 0.76, 0.73 or 0.5 jammed as at 0.8. `mjolnir poke` cannot
reach the pill, since it follows the file's block counts (0 here). The block
field sits at the root's `+0x604` ({count 2, encoded offset, definition});
the elements are at segment 1's base (`mjolnir live status`) plus the
encoded offset × 4.

**Tested with the capsule** (PC 1, 2026-10-31, Blood Gulch Slayer, the
standing capsule's upper vertex written live):

- down: `elite_legendary_13`, placed seven times and ordered to `area_0`,
  took ramp 1824 four times and jammed at (91.50, -159.64, 0.83). The other
  three times it walked over the lintel's top and dropped through the
  opening above the door (deck floor 1.70 to 2.53), at 0.8 like the rest.
  With one jammed, a capsule of 0.73 (twice) or 0.72 moved it 0.05 to 0.08

- up: eight HUD elites (bot type elite) hunting the host, who stood
  unhurtable on the north deck. At 0.70 two of them climbed the north base's

## Open

- **The copy's records**: lowered, the copy still takes about half of a
  biped's ground records (the Havok body lists its surfaces), and the AI no
  longer loses its place; what its location is read from instead is not
  traced. Other converted maps get the lowered copy at their next bake;
  none but Blood Gulch is measured.
- **A bot that will not move on the shell**: on Blood Gulch a Spartan with a
  valid location picked a new goal every half second under an area order
  and stayed where it was for 46 s (its path built, then dropped). Not
  explained; the HUD's sending away and placing again covers it.
- **Elites under low lintels**: no path data makes an AI crouch, so an
  elite passes Blood Gulch's side doors only with a lower standing capsule;
  0.70 passes both ways (tested live). Two ways to ship it: the lobby DLL
  writes the standing pill's upper vertex (z 0.52 for 0.70) in bot matches
  and puts it back after, finding it through the tag table and the block's
  encoded offset; or an override of the tag with `height standing` 0.70,
  from which the load should build the same pill (inferred from the built
  values, not tried), which lowers campaign elites too. The render model
  does not change, so an elite's head may show through low ceilings it now
  fits under (not looked at).
- **Havok proxies**: the simulation keeps 16 (`havok proxies`,
  `[TLS+0x268]`, 0x50 bytes each, the object's handle at `+0x44`). On Blood
  Gulch its four Warthogs hold one each and every live biped one: 13 with
  eight bots and a host. Twelve or more bots with one player would need more
  than 16; what a biped without one does is not known (not tried).
- **Players' campaign team elsewhere**: what else in a Megalo game reads a
  player's campaign byte now that team games with bots set it (none seen;
  player against player uses the multiplayer teams).
- **Megalo score**: Slayer's kill trigger fires on a *player* killed, so AI
  kills likely do not score; a score-to-win end needs the HUD's own count or
  a variant change.
- **Looks**: no shipped Spartan AI character (`spartans_ai` ships only as a
  stimuli character). A `new-tag` clone of `trooper` pointed at the
  `spartans` biped is the likely route.
